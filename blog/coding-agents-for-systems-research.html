Coding agents for systems research: pick the problem, then build the loop

Over the past year I built two benchmarks where coding agents do real ML-systems work, and I'm now building a harness where they design part of an inference engine on their own. The lesson I keep relearning: the model matters less than the loop around it. This post covers the one decision that comes first (which problem to give the agent) and the three parts of the loop that decide whether its results can be trusted. It ends with two ways that strong agents still get stuck.

The three projects

  • ServerBench. A coding agent gets a firewalled GPU container with model weights and a naive server that handles one request at a time, and has hours to turn it into a specialized LLM serving system. We grade by replaying stateful sessions against the server it leaves behind, with a hidden correctness check. Across 11 agent models, the best agent-built system reached 4.87× the vLLM reference on cost efficiency.
  • CompressionBench. The agent gets a pinned BF16 checkpoint, a storage budget of 8–32 GiB, an offline container with compression toolchains and a public checker. It can mix quantization, pruning, low-rank factorization and distillation. When the clock runs out, a hidden verifier it never sees judges the submission once: size, GPU memory, perplexity on hidden inputs and decode latency.
  • Agentic sparse attention (in progress). Agents design the sparse-attention policy inside an unmodified SGLang engine, from which KV pages each decode step reads down to the kernels that read them. The harness around them checks every candidate with a hidden verifier and improves itself between runs.

0Pick the right problem

Before any harness work, ask two questions about the problem. Can a program tell, without a human, whether a candidate is better? And can the agent try many candidates in the time you have? Systems performance work often answers yes to both: you can run the candidate on a workload and measure it. Audrey Cheng and colleagues make the same argument in Barbarians at the Gate, calling the approach AI-driven research for systems.

The second question is where the hard cases live. A serving system takes minutes to rebuild and a 30-minute replay to judge, so an 8-hour run gets a handful of honest measurements. A compressed 27B checkpoint takes even longer to produce and evaluate. A sparse-attention policy can be checked in minutes, which is why I chose it for the harness: the agent gets dozens of verified attempts per run instead of a few.

1Environment: the sandbox and the start point

All three projects run agents in Harbor sandboxes: a container with a GPU, the model weights, the toolchain and nothing else. ServerBench and CompressionBench cut the network once the image is built, so the agent cannot download a finished answer. The harness mounts only what the agent needs; the verifier's thresholds and correctness questions never enter the sandbox.

The start point is part of the environment, and it shapes the search. ServerBench starts from a correct but naive server, so every gain is the agent's own work and the baseline cannot be gamed. The harness starts from the opposite end: a working sparse-attention runtime with a small policy interface and presets for known methods (Quest, StreamingLLM and others), so the agent spends its hours on design rather than plumbing. A start point too far from the goal wastes the run on boilerplate; one too close leaves nothing to discover.

2Reward: define the goal as one number

The reward should be what you would actually pay for. In ServerBench it is token value per dollar of GPU cost, counted only for requests that meet the latency targets. A server that is fast but answers wrongly earns nothing, and so does one that is accurate but too slow. In the harness, a candidate is promoted only if it beats the current best by at least 1% on the same sample, with every latency and correctness gate passing.

Two details turned out to matter more than I expected. First, gates must sit outside the measurement noise: in one 8-hour harness run, three of four rejections came from a behaviour gate set at 1.10× when the candidates measured 1.101–1.107×, inside the noise band. Second, the agent will optimize anything you measure, including the harness itself. In the same run, the agent kept its session alive by appending "unchanged" lines to its notes, which reset the idle detector; that last hour cost $59 of the run's $68.

3Verification: grade files, not claims

Nothing the agent reports is graded. In ServerBench, the grader boots the server from the files the agent froze and replays sessions the agent never saw; a run whose frozen tree does not boot gets no verdict at all. CompressionBench runs its hidden verifier exactly once, after the deadline. The harness goes one step further for noisy measurements: the candidate and the current best are measured in the same verification, on the same hidden sample, because sample-to-sample variation (±0.05× in that run) is as large as most real improvements.

With these three in place, the harness's first long run was steady: in 8 hours the agent produced 13 verified submissions, promoted 7, and took its policy from 1.63× to 1.98× the end-to-end throughput of dense attention on Qwen3-8B, every step passing hidden latency and correctness gates.

Two ways strong agents still get stuck

The loop makes results trustworthy. It does not make the search good. Across our runs with DeepSeek, Sonnet and Opus models, two failure modes kept showing up, and they look the same across model families.

1 · They settle into a local optimum

On the ServerBench task that serves Qwen3.5-9B, every run of one Opus model built a capable engine (paged KV cache, prefix reuse, CUDA graphs) and then spent its remaining hours refining it. Their p90 time per output token landed between 49.8 and 60 ms. The best DeepSeek run reached 35.8 ms. None crossed the task's 23.5 ms bar by tuning. The one run that did, at 13.1 ms, added a different idea: speculative decoding with the model's own multi-token-prediction heads.

The harness shows the same shape on a smaller scale: most of its promotions were 1–3% steps on the same policy. Small verified gains are easy to find, so the agent keeps finding them.

2 · They commit to one idea and never leave it

The second failure is earlier and more costly: the agent picks a path in the first hour and treats it as fixed. Both Sonnet 5 runs on the Gemma-4 task kept the stock Hugging Face forward pass and tuned around it. One of them measured its time per token at 204–224 ms in eight of its own replays and changed nothing about the design that caused it. The runs that met the latency bar on that task had all written their own engine. A DeepSeek run on the 9B task saw its server emit doubled tokens and called them "an artifact I've seen all along" instead of questioning the path that produced them.

Across families the pattern is the same: each model made recognisably the same design decisions run after run, and those decisions predicted its result better than run-to-run noise did. More hours do not fix this, because the agent spends the extra hours on the path it already chose.

What I'm trying next

Both failures are search problems, so the fixes go into the harness rather than the prompt. Three things are in progress:

  • Separate ideas from tuning. In the two-agent version of the harness, one agent decides what to attend to and the other makes it fast, and they trade requests on a shared board. Four of those requests turned into design changes, such as making every layer sparse.
  • Make the memory remember paths, not just scores. A structured record of what was tried, and why it stalled, gives the next attempt a reason to try something else.
  • Let the harness revise its own workflow. Between phases, a meta-optimizer rewrites how the agents work; in one run it revised the workflow three times, and the kept revision produced the final best design within 7 minutes.

None of this solves the problem yet. But it changes where I spend my time: less on prompting agents, more on choosing problems with honest feedback and on building loops that push agents off the path they would otherwise never leave.
